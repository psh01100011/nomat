# 방 채팅 부하 측정

## 목적

실제 게스트 인증, 방 생성·입장, STOMP WebSocket과 Redis 방 이벤트 경로를 사용해 채팅 부하를 측정한다. 운영 코드에 테스트 전용 API를 추가하지 않는다.

## 실행 전 준비

- Docker Desktop에 시나리오 A·B는 CPU 4개 이상, C는 CPU 2개 이상을 할당한다.
- 프로젝트 루트의 `.env`가 준비되어 있어야 한다.
- 제목이 `[테스트]`로 시작하고 공개·게시 상태이며 측정 시간 동안 게임을 유지할 만큼 문제가 충분한 전용 맵이 하나 이상 필요하다. 부하 테스트의 게임 결과와 플레이 횟수가 일반 사용자 맵에 섞이는 것을 막기 위한 조건이다.
- 실행 중인 로컬 백엔드와 Grafana는 스크립트가 종료하거나 충돌 여부를 안내한다.
- 기존 MySQL·Redis Docker 볼륨은 삭제하지 않는다.

채팅 벤치마크는 Redis DB 15를 전용으로 사용하고 각 단계 시작 전에 그 DB만 초기화한다. 일반 로컬 실행이 사용하는 DB 0은 지우지 않으므로 기존 방·인증 등 로컬 Redis 데이터에는 손대지 않는다.

## 실행

기본 권장 방법은 현재 운영 후보인 B 구성에서 100명, 300명, 500명을 순서대로 실행하는 것이다.

```bash
./scripts/run-room-chat-benchmark-suite.sh B
```

처음 한 번만 실행 여부를 확인한다. 각 단계는 서버와 모니터링 컨테이너를 새로 시작해 이전 단계의 메모리와 연결 영향을 분리하며, 앞 단계에서 연결 실패·메시지 누락·오류가 발생하면 더 큰 단계는 실행하지 않는다. 전체 실행 목록은 별도의 `chat-suite` 결과 폴더에 기록된다.

연속 실행 중에는 Docker 빌드와 백엔드 준비 구간을 포함해 15초마다 현재 사용자 단계와 경과 시간이 출력된다. 본 측정이 시작되면 별도로 10초마다 연결 수, 전송·수신 수, p95 지연과 오류 수도 출력된다. 두 표시 중 하나가 계속 갱신되면 테스트가 진행 중이다.

각 단계는 대규모 사용자 준비 전에 게스트 2명으로 실제 WebSocket 연결·구독·채팅 왕복을 자동 확인한다. 사전 확인이 실패하면 해당 단계의 본 측정을 시작하지 않고 `smoke.log`와 백엔드 로그를 결과 폴더에 남긴다. 방 생성 후 실제 인원이 기대값과 같은지도 확인한다.

단계별 측정 시간 등을 바꿔 연속 실행할 수도 있다.

```bash
CHAT_BENCHMARK_DURATION_MINUTES=5 ./scripts/run-room-chat-benchmark-suite.sh B
```

한 단계만 따로 실행하려면 다음 명령을 사용한다.

```bash
./scripts/run-room-chat-benchmark.sh B 100 10 2 10
```

인자는 순서대로 다음 의미다.

```text
시나리오 사용자수 방인원 사용자별메시지간격(초) 측정시간(분)
```

스크립트가 제목이 `[테스트]`로 시작하는 공개·게시 맵을 최신순으로 확인해 필요한 문제 수를 만족하는 첫 번째 맵을 자동 선택한다. 기본 준비 2분과 측정 10분에서는 문제 제한시간을 300초로 사용하므로 최소 3문제인 맵이 선택된다. 현재 로컬 데이터에서는 `[테스트] 유튜브 100문제 임시저장` 맵이 이 조건을 만족한다.

생성된 방의 약 90%는 게임을 시작하고 약 10%는 대기 상태로 둔다. 방이 10개인 100명 이상 테스트에서는 정확히 게임방 9개와 대기방 1개가 만들어진다. 방이 10개보다 적은 짧은 확인에서는 가장 가까운 정수 비율로 반올림된다. 게임 타이머도 운영과 같은 1초 초기 지연으로 실행되어 힌트·문제 종료·다음 문제 이벤트가 채팅과 함께 발생한다.

각 WebSocket 클라이언트는 실제 프론트와 동일하게 3분마다 방 heartbeat를 전송한다. 사용자별 오류 채널도 구독하며, 메시지 제한·권한 오류 같은 애플리케이션 오류, 측정 중 연결 종료, 메시지 누락이나 중복 전달이 하나라도 발생하면 해당 단계를 실패로 판정한다. HTTP 준비 요청은 30초 안에 응답하지 않으면 경로를 포함한 오류를 남기고 중단한다.

기본 준비 부하는 120초다. 짧은 동작 확인만 할 때는 다음처럼 줄일 수 있다.

```bash
CHAT_BENCHMARK_WARMUP_SECONDS=10 ./scripts/run-room-chat-benchmark.sh B 20 10 2 1
```

100명 측정이 정상 완료된 뒤 300명, 500명 순서로 실행한다.

```bash
./scripts/run-room-chat-benchmark.sh B 300 10 2 10
./scripts/run-room-chat-benchmark.sh B 500 10 2 10
```

사용자마다 최초 전송 시점을 무작위로 분산하지만 이후 평균 2초마다 메시지 하나를 보낸다. 방당 10명이므로 메시지 하나가 정상 처리되면 같은 방의 연결 10개에 전달되어야 한다.

## 실행 중 표시

10초마다 다음 값이 출력된다.

- 현재 단계와 경과 시간
- 유지 중인 WebSocket 연결 수
- 전송 메시지와 수신 전달 수
- 현재 채팅 지연 p95
- STOMP·WebSocket·애플리케이션 오류 수

준비 단계나 100명 테스트부터 연결 실패·누락이 발생하면 더 큰 단계로 넘어가지 않는다.

## 결과

결과는 `benchmark-results/<실행ID>/`에 저장된다.

- `summary.md`: 설정, 채팅 결과와 본 측정 구간의 컨테이너별 최대 자원 사용량
- `result.json`: 자동 분석할 수 있는 상세 결과
- `container-stats.csv`: 5초 간격 컨테이너 자원 사용량
- `container-outcomes.csv`: 재시작과 OOM 여부
- `benchmark.log`: 테스트 진행 로그
- `backend.log`: 백엔드 로그

결과에는 부하 생성기 자체의 최대 메모리와 이벤트 루프 지연도 기록된다. 이 지연이 크게 상승하면 서버가 아니라 테스트를 실행한 Node.js 프로세스가 먼저 포화되었을 수 있으므로 서버 결과와 분리해 해석한다. 종료 시 대기방은 방장이 삭제하고 게임방은 모든 참여자가 차례로 퇴장한다. 정리에 실패하면 `cleanup-failures.txt`가 생성되고 테스트도 실패 처리된다.

정상 종료, 실패, 사용자 중단 시 측정 컨테이너는 자동으로 중지하고 결과 파일과 Docker volume은 유지한다. 문제 해결을 위해 컨테이너를 남겨야 할 때만 `BENCHMARK_KEEP_RUNNING=1`을 지정한다.

테스트가 끝나면 결과 폴더 경로를 공유해 결과 해석을 요청한다. 지연 기준은 측정 전에 임의로 확정하지 않고 100·300·500명 결과와 오디오 혼합 부하 결과를 비교해 정한다.
