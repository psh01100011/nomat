# NOMAT Terraform 인프라 결정 기록

## 문서 목적

- Terraform 구현 전에 운영 인프라의 선택 사항과 결정 이유를 정리한다.
- 한 번에 5개 안팎의 항목을 논의하고, 합의한 항목만 `확정`으로 변경한다.
- 비밀번호, 인증 키, 전체 이메일 주소 등 실제 비밀 값과 개인정보는 기록하지 않는다.
- 결정이 바뀌면 기존 내용을 지우기보다 `메모`에 변경 이유를 남긴다.

상태:

| 상태 | 의미 |
|---|---|
| `확정` | Terraform 구현 기준으로 사용한다. |
| `검토 필요` | 답변은 받았지만 비용·보안·구현 방식 논의가 남아 있다. |
| `미답변` | 아직 사용자 답변이 없다. |
| `보류` | 현재 구현 범위에서 제외한다. |

## 현재 합의 요약

- AWS 계정은 준비되어 있다.
- 운영 리전은 서울 `ap-northeast-2`이다.
- 운영 환경 하나만 먼저 구성한다.
- 첫 운영 월은 ALB·ASG를 포함한 현재 구성을 유지하고 월 12만~15만 원을 검증 예산으로 허용한다. 첫 달 종료 후 실제 비용과 사용량을 근거로 축소 또는 유지 여부를 다시 결정한다.
- 운영 도메인과 기본 사용자 주소는 `nomat.cloud`이며, `www.nomat.cloud`는 기본 주소로 리디렉션한다.
- 도메인 등록기관은 Gabia를 유지하고 DNS 운영은 Route 53으로 위임한다.
- API와 WebSocket은 프론트와 같은 도메인의 `/api/*` 경로를 사용한다.
- 기존 에셋 버킷은 이전하지 않고 새 버킷을 생성한다.
- 데이터와 주요 저장소에는 Terraform 삭제 방지를 적용한다.
- 갑작스러운 트래픽 증가에 대응하는 백엔드 ASG를 위해 내부 ALB를 사용하고, CloudFront VPC Origin을 유일한 외부 진입점으로 둔다.
- 백엔드와 데이터 서버는 같은 단일 가용 영역에서 운영하고, ALB만 요구 사항에 따라 두 가용 영역에 배치한다.
- 백엔드와 데이터 EC2는 같은 가용 영역의 public subnet에 두고 NAT는 운영하지 않는다.
- EC2는 ARM64 Graviton 계열과 Ubuntu Server 24.04 LTS를 사용한다.
- 백엔드 ASG는 평균 CPU 60%를 확장 목표로 사용하고, CPU 80%가 2분간 유지되면 긴급하게 한 대를 추가한다. 축소는 평균 CPU 25% 미만이 30분간 유지될 때 별도 정책으로 수행한다.
- 백엔드 루트 EBS는 `gp3` 30GiB로 시작한다.
- 운영 설정과 비밀 값은 SSM Parameter Store의 `/nomat/prod/...` 경로로 관리한다.
- 운영 메일은 Amazon SES API로 발송하고, AWS 접근에는 정적 액세스 키 없이 IAM Role만 사용한다.

### 첫 운영 월 비용 정책

- 첫 달은 비용을 최소화하기보다 실제 사용자 유입과 실시간 게임·오디오 처리 부하를 확인하는 검증 기간으로 운영한다.
- ALB, 백엔드 ASG `min=1`, `desired=1`, `max=3`, 데이터 EC2 1대 구성을 첫 달 동안 유지한다.
- 내부 ALB 전환으로 ALB용 공인 IPv4 2개가 제거되므로 예상 정상 범위는 월 11만~14만 원으로 조정한다. 첫 달 검증 예산은 15만 원까지 허용하고, 실제 누적 비용 7만·10만·13만 원과 예상 비용 15만 원 초과에 알림을 보낸다.
- Terraform의 AWS Budgets 금액은 적용 시점의 보수적인 원·달러 환율로 환산하며 세금 포함 비용을 기준으로 확인한다.
- 비용 알림은 자원을 자동 중단하지 않는다. 과금 폭증 방지는 ASG 최대 3대, 로그 보존 기간, S3 Lifecycle 같은 서비스별 제한으로 보완한다.
- 첫 달 종료 시 총비용과 서비스별 비용, ALB 요청·연결량, ASG 평균·최대 인스턴스 수, 백엔드 CPU·메모리, 동시 게임방·WebSocket 수, 오디오 대기 시간과 처리량을 함께 검토한다.
- 사용량이 적으면 ALB 제거 또는 더 단순한 단일 백엔드 구성을 검토하고, 실제 확장 수요가 확인되면 현재 구성을 유지하며 장기 할인 적용 여부를 별도로 판단한다.

### 운영 DB migration 규칙

- DB 변경 작업을 시작할 때 추가형과 파괴형을 먼저 분류한다.
- 구버전과 신버전 백엔드가 변경 중인 schema를 동시에 사용할 수 있는지 확인한다.
- column·table 추가처럼 하위 호환되는 변경은 같은 배포에 포함할 수 있다.
- column·table 삭제, 이름 변경, 호환되지 않는 타입 변경, 즉시 `NOT NULL` 적용은 한 번에 배포하지 않는다.
- 파괴적 변경은 새 구조 추가, 데이터 backfill 및 코드 전환, 이전 구조 삭제 순서로 나눈다.
- migration이 포함된 작업은 구현 전에 배포 단계와 rollback 방법을 사용자와 먼저 합의한다.
- CI에서 기존 migration checksum과 명명 규칙을 검증하고, 운영 승인 전에 신규 SQL을 수동 확인한다.
- 신규 인스턴스의 migration 또는 schema 검증이 실패하면 ALB에 등록하지 않고 기존 정상 인스턴스를 유지한다.

### 게임 종료와 WebSocket 정리 정책

- 대기방은 활동 heartbeat와 관계없이 생성 후 30분 안에 게임이 시작되지 않으면 종료한다.
- 게임 시작과 대기방 만료는 같은 방 단위 분산 잠금으로 처리하며, 게임이 먼저 시작되면 대기방 만료 예약을 취소한다. 게임방 자체에는 30분 제한을 적용하지 않는다.
- 대기방 만료 시 `ROOM_CLOSED` 이벤트와 `WAITING_TIMEOUT` 사유를 전송하고, 프론트는 방 목록으로 이동해 종료 이유를 안내한다.
- 게임 결과 저장이 완료되면 백엔드는 최종 `GAME_ENDED` 이벤트를 전달하고 Redis의 방, 게임 상태, 초대 정보, 사용자별 현재 방 연결과 남은 타이머를 삭제한다.
- 프론트는 `GAME_ENDED` 이벤트로 최종 점수와 결과 화면 상태를 먼저 확정한 뒤 room heartbeat를 중단하고 WebSocket 연결을 정상 종료한다.
- 결과 화면은 이미 수신한 로컬 상태로 계속 표시하므로 WebSocket과 Redis 방 데이터가 없어도 현재 화면을 유지한다.
- 결과 화면을 새로고침하거나 떠난 뒤에는 삭제된 실시간 방으로 복귀하지 않는다. 영구 보관이 필요한 결과는 MySQL의 게임 결과·플레이 기록을 사용한다.
- 배포 또는 ASG 축소 시 종료 대기 여부는 원시 WebSocket 연결 수가 아니라, 해당 서버 연결 중 Redis에 실제로 남아 있는 `WAITING` 또는 `PLAYING` 방을 기준으로 판단한다.
- 이미 종료·삭제된 방의 결과 화면 연결이나 어느 방에도 속하지 않은 연결은 기존 서버 종료를 막지 않는다.

### SSM과 IAM 적용 원칙

- 표준 등급 SSM Parameter Store를 사용하고, 현재 규모에서는 고급 파라미터를 사용하지 않는다.
- 비밀 값 이름에는 비밀번호나 토큰 값 자체를 포함하지 않는다.
- 비밀 값은 `SecureString`으로 저장하고 초기에는 AWS 관리형 `alias/aws/ssm` 키를 사용한다.
- 백엔드 Role은 필요한 `/nomat/prod/...` 경로의 조회 권한만 가지며 값 생성·수정 권한은 갖지 않는다.
- Terraform의 `sensitive` 표시는 화면 노출만 줄일 뿐 state 저장을 막지 못하므로 실제 비밀 값을 Terraform 입력으로 전달하지 않는다.
- 저장소에는 필요한 파라미터 이름 목록과 대화형 초기 입력 도구를 제공한다. 입력 값은 화면과 파일에 남기지 않고 AWS SSM으로 바로 전송하며, 누락된 필수 값도 확인할 수 있게 한다.
- GitHub Actions는 추후 OIDC로 AWS Role을 맡도록 구성하며 장기 액세스 키를 GitHub Secret에도 저장하지 않는다.

### 최초 bootstrap 순서

1. Terraform state, 네트워크, IAM, SSM 경로와 데이터 계층 등 기반 인프라를 먼저 생성한다.
2. 별도 초기화 도구로 실제 설정과 비밀 값을 SSM Parameter Store에 입력한다.
3. 필수 파라미터가 모두 존재하고 데이터 계층에 연결할 수 있는지 검증한다.
4. 검증이 완료된 뒤 백엔드 Launch Template, ASG와 ALB target 등록을 생성한다.
5. 비밀 값이 누락되면 백엔드 생성 단계로 넘어가지 않으며 임시 비밀 값은 사용하지 않는다.

### 모니터링 구성 구분

- 각 EC2의 애플리케이션과 Exporter는 현재 상태를 숫자 지표로 노출하지만 장기간 저장하지 않는다.
- 데이터 EC2의 중앙 Prometheus가 각 대상의 지표를 주기적으로 가져와 15일·5GB 범위에서 저장한다.
- 로컬 Grafana는 데이터를 저장하지 않고 Prometheus와 로그 저장소를 조회해 화면으로 보여준다.
- Prometheus는 수집기이자 저장소이므로 로컬 PC에 두지 않는다. 로컬 PC가 꺼진 시간의 지표는 사후에 다시 수집할 수 없고, ASG로 교체되는 백엔드 대상에 안정적으로 접근하기도 어렵다.
- Prometheus와 Exporter 포트는 인터넷에 공개하지 않고 모니터링 보안 그룹과 SSM 터널을 통해서만 접근한다.
- 데이터 EC2 자체의 상태 검사 실패, 디스크 사용량, 필수 프로세스 중단은 CloudWatch Alarm이 외부에서 감시하고 SNS로 알린다. 애플리케이션과 MySQL·Redis의 세부 성능 지표는 Prometheus가 담당한다.

### 해결된 교차 점검

- DNS는 Route 53으로 위임한다. Terraform이 public hosted zone을 만든 뒤 사용자가 Gabia에 NS 레코드를 한 번 반영하고, 이후 ACM 검증·CloudFront 주소·SES DKIM 레코드는 Terraform이 관리한다.
- 기본 사용자 주소는 `nomat.cloud`로 사용하고 `www.nomat.cloud`는 같은 경로의 `https://nomat.cloud`로 영구 리디렉션한다.
- 백엔드 ASG는 평균 CPU 60% 목표 추적과 CPU 80% 긴급 확장 정책을 사용한다. 목표 추적의 자동 축소는 끄고, 평균 CPU 25% 미만이 30분간 유지될 때 별도 정책으로 한 대씩 축소한다. 축소 시 WebSocket 연결은 draining 후 재접속시키고 오디오 워커는 신규 선점을 중단한 뒤 진행 중 작업을 정리한다.
- 첫 운영 월은 현재 ALB·ASG 구성을 유지하고 월 12만~15만 원을 검증 예산으로 허용한다. 첫 달 종료 후 실제 비용과 사용량을 기준으로 축소 또는 유지 여부를 다시 결정한다.
- 비용·장애 알림용 SNS topic은 Terraform으로 관리하되 실제 이메일 구독과 확인은 Terraform 밖에서 수행하여 전체 이메일 주소를 코드와 state에 저장하지 않는다.
- Redis는 영구 EBS가 유지된 프로세스·EC2 재시작에서는 AOF/RDB로 복구하고, 데이터 볼륨 유실이나 오래된 snapshot 복구에서는 진행 중 방과 게임 상태를 포기한다.
- 최초 구축은 기반 인프라 생성, SSM 비밀 값 입력, 필수 값 검증, 백엔드 ASG 생성 순서로 분리한다.
- 내부 ALB를 두 private subnet에 배치하고 CloudFront VPC Origin의 서비스 관리형 보안 그룹에서 오는 요청만 허용한다. ALB는 공인 주소를 갖지 않으므로 인터넷에서 직접 접근할 수 없다. `/api/*`와 WebSocket behavior는 캐시를 끄고 인증·연결에 필요한 헤더를 전달한다.
- 데이터 EC2는 고정 private IP를 가진 별도 ENI와 영구 데이터 EBS를 사용한다. 장애 교체 시 새 인스턴스에 같은 ENI와 EBS를 재연결하는 복구 절차를 마련한다.
- 데이터 EC2와 필수 프로세스의 외부 생존 감시는 CloudWatch Alarm과 SNS가 담당하고, Prometheus는 세부 애플리케이션 지표를 담당한다.
